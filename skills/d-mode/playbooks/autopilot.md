### Autopilot

**You own the verdicts, never the changes. One owner carries each queue item from build to verified, and nothing lands on `main` until a verifier that never wrote the code has proven the code that lands.**

A verdict covers one patch. A rebase that leaves `git patch-id` unchanged keeps the verdict, and any other change to the patch needs a fresh check.

1. **The operator's gates come first.** The grant covers only the queue's items. Items the operator names as theirs stop at verified. A request to state the plan is not a go. "Don't push" or "I'll land them" means every item stops at verified, on its own branch, and nobody pushes.
2. **Spawn one owner per item, each in its own worktree.** Each owner is a `dstack:d-agent` with `isolation: "worktree"` on a branch named `d/<item-slug>` off `main`. It builds the change, proves it on the real artifact, cleans the diff and commits per steps 1 to 3 of `playbooks/commit-and-push.md`, runs the gate, and reports its branch, head SHA, and `git patch-id`. Owners do not push and do not touch `main`.
3. **Run owners in parallel off `main`.** Branch an item off another item's branch only when it builds on that item, and land the lower one first.
4. **Verify each item with an agent that did not write it.** One verifier per item on the `swarm workers` model, per the **swarm** skill. It checks out the reported SHA, reruns the gate, drives the changed behavior the way a user would (the project's `verify-<app>` skill when one exists), audits the diff, and reports `PASS`, `PASS+NOTES`, or `FAIL` with the commands and their output. A green gate alone is not a verdict, because it does not run the change as a user would. Block an item only for a problem you can show: a failing run at its head, or a doc line the change made wrong. A problem `main` already has does not block unless the change copies it or newly reaches it.
5. **Land verified items one at a time.** Landing is serial, because `main` is shared state (the **separate-before-serializing-shared-state** principle skill). For each item with `PASS` or `PASS+NOTES`, in queue order: in its worktree `git rebase main`, compare `git patch-id` before and after, and send the item back to step 4 when the patch changed. Then in the main checkout `git merge --ff-only d/<item-slug>` and run steps 5 to 8 of `playbooks/commit-and-push.md`. If its step 7 rebases again because `origin/main` moved, compare `git patch-id` once more before the push, and send the item back to step 4 when the patch changed. A `FAIL` item goes back to a fresh owner with the verifier's report, and the items behind it keep moving.
6. **Keep the run honest.** Log each owner, verdict, and landing as a row per the **show-me-your-work** skill. On the operator's go for a long queue, arm Claude Code's built-in `/loop` at a one-hour interval to audit until no delegated work is left. An agent is stuck when it errors or shows nothing new past the time agents of its kind have taken. Replace a stuck agent with a fresh one that gets the original brief and the branch. Anything that loosens a gate, such as a skipped test or a raised budget, needs a verifier's proof and then your own countersign.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its branch.

**Reply:** catch the operator up per the **ketchup** skill: each item's state and verdict, what landed as `<old sha>..<new sha>`, countersigns and why, open operator gates, and parked follow-ups, with each branch name and the trail path.
